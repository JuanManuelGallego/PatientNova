# AGENTS.md

## Repository

- `Server/`: Node/TypeScript backend, Prisma, pg-boss; unit and real-Postgres integration tests.
- `Portal/`: Next.js frontend; Playwright e2e tests.
- `ops/db-backup/`: nightly encrypted database backup (Railway cron); `smoke-test.sh` runs it end to end, and setup is in `docs/operations.md`.
- Backend `src/` paths below are relative to `Server/`; frontend paths to `Portal/`.

## Tests and configuration

From `Server/`, start the disposable database on port 5433 and run integration tests:

```bash
docker compose -f docker-compose.test.yml up -d
pnpm run test:integration
```

- The Vitest `integration` project (`test/integration/**/*.test.ts`) loads `.env.test` via setup, runs serially, and truncates all `public` tables between tests. Never use dev/prod: `DATABASE_URL` must contain `test`.
- Adding `requireEnv(...)` in `src/utils/config/config.ts` requires updating `.env.test`, `.github/workflows/ci.yml` (CI supplies env directly), `.env.example`, and local `Server/.env` (used by unit tests).
- After changing `schema.prisma`, run `pnpm exec prisma generate`; the committed `generated/prisma` client is typechecked.
- Unit tests (`test/unit/**/*.test.ts`) mock Prisma/DB. Integration tests cover repositories, services and HTTP routes; consult the tests for coverage.
- Reuse `test/integration/helpers.ts`: entity factories, `appointmentTimeRange`, `futureDate`, `unique`, `makeRes`, and `invokeRoute`. The latter runs validation/middleware and waits for `asyncHandler` to settle.
- `asyncHandler` writes errors through `handleError(res, err)`, does not call `next(err)`, and drops its promise. Direct-handler tests must flush microtasks and assert `res.statusCode`/`res.body`.
- Mock external services at module boundaries: `twilio`, `src/twilio/client.js`, `src/brevo/email-client.js`, and `src/scheduler/dispatch.js`. Stub `fetch` for Brevo/Turnstile; never make real network calls in integration tests.
- Mock `reminderJobManager` for reminder-service pg-boss operations to avoid transaction/connection-pool deadlocks. `scheduler.integration.test.ts` explicitly starts/stops real pg-boss and tests `send-reminder`.
- Route-test `authReq` includes CSRF: preserve `csrfHeaders()` when overriding headers.
- Limiter tests (`test/integration/portal/portal-abuse.integration.test.ts`) build a fresh `buildPortalApp()` per test (fresh in-memory buckets) and give each client its own `X-Forwarded-For`. Named limiters run after the class parser; only `public-ip`/`portal-ip` run before parsing.

## Database, calendar and audit integrity

- Generated migrations can drop objects absent from Prisma's schema. Inspect SQL and remove generated `DROP INDEX`/`DROP CONSTRAINT` for these raw-SQL objects; add new ones to this list:
  - `patients_userId_emailHash_active_key`: unique `(userId, emailHash) WHERE isDeleted = false`, migration `20261019000000_encrypt_patient_pii`.
  - `appointments_no_provider_overlap`: exclusion constraint, migration `20261007000000_appointment_no_overlap`; requires `btree_gist`.
  - `patient_consents_active_key`: unique `(patientId, kind, policyVersion) WHERE revokedAt IS NULL`, migration `20261101000000_portal_auth`.
  - `booking_requests_no_hold_overlap`: exclusion constraint over `booking_requests` with `status IN ('PENDING','UNCONFIRMED')` per provider (`tsrange(startAt, endAt, '[)')`), created in `20261106000000_booking_requests`, redefined in `20261115000100_booking_unconfirmed_hold`; requires `btree_gist`. It cannot see the clock, so `bookingRequestService.createUnconfirmedWithin` first expires stale holds under the lock.
- Transactions creating/moving appointments or blocked time call `withProviderLock(tx, userId)` FIRST (`src/utils/prisma/provider-lock.ts`), then validate and write on that same `tx`. Compose with `createWithin`/`updateWithin`.
- Conflicts are provider-wide over non-deleted SCHEDULED/CONFIRMED appointments (`ACTIVE_STATUSES`), using half-open intervals. Map the exclusion backstop (appointments and holds) through `isAppointmentOverlapViolation` to a neutral 409.
- A live hold (`BookingRequest` PENDING or UNCONFIRMED with `holdExpiresAt > now`, `src/booking-requests/`) blocks its slot for patients: `loadLiveHolds` feeds the slot engine's `holds` (buffer included), so public slots and `isSlotFree` count both. The provider always wins over a hold it cannot see: `checkConflict` (`findLiveHoldOverlap`) throws `AppointmentHoldConflictError` (mapped to `SlotUnavailableError` on portal paths) only for PENDING requests with `confirmedAt`, never for UNCONFIRMED ones. A click after the provider took the time is refused and the hold released: `confirmWithin` reruns the slot rules (`isHeldSlotFree`: `isSlotFree` with `excludeRequestId`, buffer, availability and grid included, the lead time as of the hold's `createdAt`) in either mode, and `createWithin`'s conflict stays the backstop. Expiry is by clock, never by the cron. Pass `excludeRequestId` (`slotRules` options, `createWithin` opts) only when resolving that same request. Holds last `min(now + 48h, startAt)`.
- `BookingRequest.email/verifiedPhone/name/lastName/phone` are encrypted, with `emailHash` and `verifiedPhoneHash` blind indexes; audit rows for requests never carry them. `phone` is typed, never proven, and is never queried.
- Transactional `logAudit` calls require both `tx` and `required: true`; swallowing an audit error leaves the transaction aborted. Best-effort audit is only for non-transactional legacy paths.
- Portal actions use `runInAuditContext(portalPatientAuditContext({...}), fn)` for `ActionSource.PUBLIC_PORTAL` and a hashed actor id. Portal actor ids come only from `portalActorId` (`src/audit-log/audit-actors.ts`); actions before a contact is proven (start, release, an unsent link) use `portalAnonymousAuditContext` (`PORTAL_ANONYMOUS_ACTOR_ID`), never a contact's actor. `resolvePortalPatient` (and portal patient creation) bind the matched record through `bindAuditPortalPatient`, so later rows in that action carry `AuditLog.portalPatientId`. `GET /v1/audit-logs?portalPatientId=` returns PUBLIC_PORTAL rows linked to the record plus unlinked rows (requests, confirmations) of the actors of its current email and numbers, never an unverified number; never filter portal activity by actor id alone. The email form of `portalActorHash` must stay byte-identical: stored rows depend on it.
- New server `EntityType`/`ActionType` values go into `Portal/src/types/AuditLog.ts` (labels) in the same PR; the pills only fall back to the raw value.

## Security and PII

- Use only `src/auth/tokens.ts` for JWTs (HS256, issuer, per-kind audience; separate `PORTAL_AUTH_SECRET`). Never call `jwt.sign/verify` directly.
- Provider cookie-authenticated writes require `X-CSRF-Token = createCsrfToken(sid, AUTH_SECRET)`; GET/HEAD/OPTIONS and Bearer requests are exempt. `fetchWithAuth` obtains it from `GET /v1/auth/csrf` and keeps it in memory.
- Twilio/Brevo webhook signature checks are always enforced, with no environment bypass. Test with real signatures or mocked middleware.
- Unset/blank `NODE_ENV` resolves to production and requires `ENCRYPTION_KEY`. Set `NODE_ENV=development` explicitly locally.
- Log paths with `loggedPath(req)`, never `req.originalUrl` (queries may carry PII). Use `maskEmail`/`maskPhone` under `maskedEmail`/`maskedTo`; logger redaction is only a safety net.
- Errors reach Sentry: never interpolate names, notes, emails or phones. `scrubText` only masks well-formed emails and phone-like numbers. Sentry stays opt-in via DSN, with restricted `dataCollection` and `scrubEvent`/`scrubBrowserEvent`; see `docs/operations.md`.
- Encrypted fields: `Patient.name/lastName/email/whatsappNumber/smsNumber`, `Reminder.to/subject`, `MedicalRecord.name/birthPlace`. Never SQL-filter, sort or `contains` on ciphertext.
- Search through `patientSearchWhere`/`medicalRecordNameWhere` (`src/utils/encryption/pii-search.ts`); exact lookups use blind indexes (`emailHash`, `toHash`, etc.). The Prisma extension maintains `BLIND_INDEXES`; never set them manually.
- Raw SQL bypasses encryption: never `$executeRaw` encrypted fields outside `backfill-pii.ts`, `reencrypt-pii.ts` and the constants of `patient-erasure.service.ts`. New PII fields require `ENCRYPTED_FIELDS`, `BLIND_INDEXES` if searched, a `TEXT` column, `REENCRYPT_TABLES` (`reencrypt-pii.ts`) for a new model, and tests.
- Global JSON/urlencoded limit: `100kb`. Mount larger parsers BEFORE it: `/v1/users` 2mb, `/v1/consent-document` and `/v1/medical-records` 15mb, `/webhooks/brevo` 1mb. First parser wins. Limiters run before parsing; global per-IP limiting skips signature-authenticated `/webhooks/*`. `trust proxy` is exactly 1 hop.

## Public API, booking links and sessions

- Mount only through `createPublicApiRouter()` (anonymous, no cookies/credentials) or `createPortalSessionRouter()` (credentialed, exact Origin on mutations), BEFORE provider CORS, body parsers and global limiter in `app.ts`. Public/session bodies are limited to 10kb.
- `createPublicLimiter` is coarse, in-memory, per-instance/per-IP and runs before parsing. Enforce brute-force-sensitive counters on domain records transactionally under the provider lock (`enforceCaps`, `checkPaidCaps`), never solely through HTTP limits.
- Public endpoints sending messages/creating records use `requireCaptcha(createCaptchaVerifier(), '<action>')` after limiter/parser. `TurnstileWidget` sends matching action and `captchaToken`; no CAPTCHA on confirmation view/confirm/release or session routes (the token is the proof).
- Turnstile checks hostname, action and `challenge_ts`, failing closed (outage: 503). No environment bypass; `CAPTCHA_SECRET` is required. `.env.test`/CI use Cloudflare's test secret; only `isTurnstileTestSecret` plus testing metadata may skip hostname/action checks. Keep Portal CSP access to `https://challenges.cloudflare.com`; missing `NEXT_PUBLIC_TURNSTILE_SITE_KEY` must show an error and block submission.
- Patients book without logging in: `POST /v1/public/providers/:slug/bookings` (`bookingStartService.start`, limiter `portal-booking-ip` 10/15min, `requireCaptcha('booking')`) holds the slot as an `UNCONFIRMED` `BookingRequest` for `min(now + 15 min, startAt)` and sends a link `${PORTAL_URL}/book/confirmar/<token>` to the contact (`EMAIL` or `WHATSAPP`, the patient's choice; never SMS). A link that cannot be sent releases the hold (`resolvedBy: 'system'`, audit) and answers `ConfirmationLinkNotSentError` (503): never "check your inbox" for a message that did not leave. `POST /v1/public/booking-confirmations/{view,confirm,release}` (one `booking-confirm-ip` bucket, 20/15min) are anonymous, with no CAPTCHA. Only `confirm` (POST, the button) changes state: opening or scanning the link never does. `confirmar` is a reserved slug.
- Tokens: 32 random bytes (`request-token.ts`), stored only as SHA-256 (`confirmTokenHash`, `releaseTokenHash`). They travel only in JSON bodies, never in an API URL, log, audit row or Sentry; the link's own path is the one place a token appears, so the page sets `referrer: no-referrer` and logs use `loggedPath(req)`. `releaseToken` (returned by start, held in component state) frees a mistaken hold and is never sent in a message. Unknown tokens answer 404; every other state is answered by `view`, with no patient name or contact.
- Start and view touch no patient: no patient lookup or write, consent row or appointment before the click, and the 202 has one shape for every contact. Start order under the provider lock: live (`resolveBookingMode`) -> bookable type/location -> `isSlotFree` (holds counted) -> `enforceCaps` (3 live UNCONFIRMED per contact, 5 live UNCONFIRMED per provider, `EMAIL_SENDS_PER_HOUR` = 5 rows per email per provider per hour in any status, WhatsApp paid caps; never anything the contact did after proving it, which would reveal its requests to whoever types it) -> `createUnconfirmedWithin`. Brute-force counters live on these rows, not in HTTP limits.
- WhatsApp paid caps are counted on `booking_requests` rows with `contactChannel = WHATSAPP`, under the lock and before the hold (`portal-paid-caps.ts`): 3 per number per hour, 30 distinct numbers per provider per hour, `PORTAL_WHATSAPP_DAILY_CAP` distinct numbers per 24h across providers (default 60). A hit cap creates nothing, answers `WhatsAppUnavailableError` (409, use email) and logs at error level `Portal WhatsApp cap reached: <phone-cap|provider-paid-cap|paid-daily-cap>` with no PII: error tracking receives only the message.
- Self-serve ("Mis citas": session, consent, list, cancel, reschedule) is deferred behind `ENABLE_SELF_SERVE=true` (default off): `createPortalSessionRouter()` is empty and every `/v1/portal` path is a 404; `/users/me` exposes `selfServeEnabled` and the public profile `selfServe`; patient emails carry the "Mis citas" link (`appointmentsUrl`) only while it is on. Nothing issues a session now (the OTP login and its table are gone), so the rules that follow are for future code. A session proves a `PortalContact` (`src/portal/portal-contact.ts`), an email or a phone, never a patient; read `session.contact`. Portal JWTs carry random `sid`; CSRF uses `createCsrfToken(sid, PORTAL_AUTH_SECRET)`; session routes use `portalSessionGuard`; read only the `portal_session` cookie with `verifyPortalToken`, recheck `isPortalReachable` each request and return one `401 'Invalid session'`; scope by `req.portal`, never client ids.
- Match patients only through `resolvePortalPatient` (`src/portal/patient-resolution.ts`). Its `patient`/`unavailable`/`none` result must not reveal patient existence via response shape/status.
- A phone identifies a patient only when exactly one trusted active record holds it (`classifyPhoneMatch`): an SMS number, or a WhatsApp number not flagged. Unverified records do not count, so a typed number cannot lock out its real holder. Any active revoked match fails closed for the whole number; several or only-unverified matches are `unavailable, review: true`. Never add a "who are you?" picker: it would show a family member's name to whoever holds the phone.
- Typed numbers are never identities. `Patient.whatsappUnverified` is set whenever a number from the booking form is written, and cleared only when the provider changes the number, sets `reminderChannel = WHATSAPP`, or links the record to a request whose link was confirmed on that same number. A WhatsApp booking never takes a typed phone (`patient.phone` is 400): the number is the contact that confirmed.
- Consent uses `ensureCurrentConsent` (`src/patient-consents/`), idempotent on `patient_consents_active_key`, auditing inside `tx` only on insertion. Only the server selects `PRIVACY_POLICY_VERSION`.
- Consent gates only the portal. Revocation is the operator command `consent:revoke` (`src/patient-consents/consent-revocation.service.ts`, procedure in `docs/compliance-patient-data.md` section 4). It never cancels care. `Patient.messagesStoppedAt` makes `resolvePatientRoute` return null, and the send workers cancel anything queued. Approval refuses a request older than a revocation (`findRevokedSince`).
- The authorization text has one source, `Portal/src/config/consentText.ts`. Changing it, the policy or the patient conditions bumps `PRIVACY_POLICY_VERSION` and adds a folder under `docs/legal/versions/`, because consent rows store only the version. Booking needs the clinic's legal identity plus a public phone or WhatsApp (`hasLegalIdentity` readiness), which is the real alternative that keeps the portal voluntary.
- Two commands rewrite audit rows through raw SQL: `patient:erase` (`src/patients/patient-erasure.service.ts`) with constants, `pii:reencrypt` (`reencrypt-pii.ts`) with ciphertext only. Audit rows keep names until erasure.

## Booking and patient actions

- Booking settings (`src/booking-settings/`, `/v1/booking`) require `requirePortalEnabled` (404 with portal off); `/users/me` exposes `portalEnabled`.
- Availability uses ISO weekdays and half-open wall-clock minute ranges in `User.timezone`, a 5-minute grid and no midnight crossing. Resolve per date, never fixed offsets; replace the week atomically under `withProviderLock`.
- Virtual locations may be `bookableOnline`. `Appointment.meetingStatus` is `NOT_REQUIRED | PENDING | NEEDS_LINK | READY`, set only through `resolveMeeting` (`src/appointments/appointment-meeting.service.ts`): virtual without a URL is allowed only on portal create (`createWithin` option `meetingPending`) or while `PENDING`/`NEEDS_LINK`; every provider-created virtual appointment still needs a URL.
- Portal virtual bookings: `auto` (scheduler on + usable Google connection, read on `tx`) creates `PENDING` and enqueues `provision-meet` on `tx` (`singletonKey`); otherwise `manual` → `NEEDS_LINK`. Call Google only in the `provision-meet` worker, never inside a transaction; it sets the link through `updateWithin` under the lock, and falls back to `NEEDS_LINK` (`markNeedsLink`, `src/portal/portal-meeting.service.ts`) on provider-side errors or the final attempt. `sweep-pending-meetings` moves `PENDING` older than 30 min.
- Readiness is checked when enabling (slug, availability, bookable type/location). Later loss of readiness keeps `bookingEnabled` but reports `live: false`. Use `bookingSettingsService.isBookingLive(userId, tx)` after the provider lock for booking; pages/images/confirmation view/sessions need only `isPortalReachable`. Never re-derive these checks. Profile/session expose `bookingOpen`.
- Reachable means portal on, provider active/not deleted, with a slug. Live additionally requires booking enabled and ready; paused/not-ready booking still serves the profile; confirming refuses (the hold is released) and, with self-serve, listing and cancellation keep working.
- Resolve slugs only with `publicBookingService.resolveProvider(slug, 'reachable' | 'live')`: reachable for profile/images/start, live for slots (start re-checks `resolveBookingMode` under the lock). Invalid, unknown or unavailable providers share `ProviderNotFoundError`; closed profiles list no types/locations.
- Availability uses `generateSlots`/`isSlotAvailable` and `ACTIVE_STATUSES` appointments plus non-deleted blocked time. Public DTOs are allow-lists: no `userId`, private contacts (`phoneNumber`/`whatsappNumber`), settings or location `instructions`. The only exceptions are the provider's public profile (`bio`, `specialty`, `publicPhone`, `publicWhatsapp`, `legal`, edited through booking settings and also shown while booking is paused) and `reschedulePolicy`, non-null only while patients can reschedule (booking open, `AUTO_CONFIRM`). Expose `lastBookableDate` for paging.
- Public images serve only allowed data-URL image bytes with `Cross-Origin-Resource-Policy: cross-origin`; Portal CSP `img-src` allows the API origin.
- Book only through `bookingConfirmationService.confirm` (`booking-confirmation.service.ts`), after `start` above. Under `withProviderLock`, on the row re-read on `tx`: anything but a live UNCONFIRMED row commits nothing and answers its state -> `resolveBookingMode` -> bookable type/location -> slot rules again (`isHeldSlotFree`, else `SlotUnavailableError`) -> `REQUIRE_APPROVAL`: `enterInboxWithin` (3 live confirmed PENDING per contact, else `PortalRequestLimitError`; cap 50 PENDING per provider; UNCONFIRMED -> PENDING with `confirmedAt` and `holdExpiry(now, startAt)`, 48h; required `BOOKING_REQUEST` audit; `received` notice) -> otherwise `bookForIdentityWithin` (`resolvePortalPatient` -> create or reuse the patient, new ones `source: PORTAL`, existing ones never modified -> upcoming cap -> `findRevokedSince` -> `ensureCurrentConsent` with the stored evidence -> `createPortalAppointmentWithin` with `excludeRequestId`) -> request APPROVED (`resolvedBy: 'patient'`) + required audit. A refused click (slot, provider, type or cap) releases the hold in its own transaction (CANCELLED, `resolvedBy: 'system'`, audit) and answers 409 (404 for provider/type/location); the page shows `unavailable` with the provider's contact. The view state of a request that did not end in a live appointment (rejected, expired after confirming, or approved whose appointment was cancelled or deleted) is `unavailable`. Map conflicts, including 23P01, to neutral `SlotUnavailableError` without others' times. Server derives price/duration/end/status. Lists use `PortalAppointmentDto`.
- Approval mode (`REQUIRE_APPROVAL`): confirming sends the request to the provider; the patient sees `requested` ("Solicitud enviada"), with no receipt email. Reschedule keeps requiring `AUTO_CONFIRM` (`requireSelfBooking`). Own requests (self-serve) go only through `ownRequestWhere` (`emailHash` or `verifiedPhoneHash`); `listLiveOwn`/`findLiveOwn` see only PENDING with `confirmedAt` set. `POST /requests/:id/cancel` (`portal-change-ip` + `portalSessionGuard`): lock -> own live PENDING -> CANCELLED + audit; every miss is `PortalRequestNotFoundError` (404); works while booking is paused.
- Review routing (6.6): at confirm in auto-confirm, a `resolvePortalPatient` result `{ kind: 'unavailable', review: true }` (inactive or deleted-only match) makes `bookForIdentityWithin` return `review` and the request enters the inbox as `BookingRequestKind.REVIEW` (the patient sees `requested`); `review: false` (revoked `portalAccessEnabled`) stays `PortalBookingUnavailableError`. The click proves control of the contact. Only the booking path reads `review`.
- Provider inbox (`/v1/booking-requests`, `authenticate` + `requirePortalEnabled` + `requireAdmin`; service `booking-request-review.service.ts`): list by tab (`pending | resolved | expired`, effective status: PENDING past `holdExpiresAt` is EXPIRED), `count`, detail with `candidates` computed at view time (never stored). `candidates` are found by the verified contact only. The provider never sees UNCONFIRMED rows, nor EXPIRED/CANCELLED rows with `confirmedAt = null` (inbox, count, detail, notices). Approve: lock -> PENDING and live (else `BookingRequestNotPendingError` 409) -> patient (`existingPatientId` picks an active candidate; `restorePatientId` restores a deleted one, 409 while an active one holds the email, allowed alongside others sharing a number; else reuse the contact's single match, for a number only a single trusted one, reactivating INACTIVE; else create `source: PORTAL`) -> `ensureCurrentConsent(..., request.consentAcceptedAt)` -> `createPortalAppointmentWithin` with `excludeRequestId` -> APPROVED with ids -> required audits -> `enqueuePortalNotifications('approved', ...)` (patient only; none while the Meet link is PENDING). Any failure rolls back and the request stays PENDING. Reject releases the slot and sends a neutral patient email. Approval does not need `isBookingLive`.
- Cancel/reschedule use `portal-change-ip` + `portalSessionGuard`. Cancel order: lock -> `requireConsentedPatient` -> `findOwn` -> `canCancel`. Every missing/ineligible cancel target shares `PortalAppointmentNotFoundError` (404). Any upcoming active appointment can be cancelled, including provider-created ones and while booking is paused.
- Reschedule order: lock -> live + `AUTO_CONFIRM` (404) -> consented patient -> `findOwn`/`canCancel` (404) -> `canReschedule` (409). It requires `source=PORTAL`, still-bookable type/location, remaining `maxPatientReschedules` and sufficient `minRescheduleNoticeHours`; otherwise `PortalRescheduleUnavailableError`. Increment `patientRescheduleCount` only on successful patient moves.
- Reuse `portalActionContext` and `canCancel`/`canReschedule` (`src/portal/portal-appointment-actions.ts`); expose flags through `PortalAppointmentDto`. Frontend actions use these flags only.
- Reschedule body is strictly `{ startUtc, patientTimezone }`; unchanged start is 400. Use current type duration and `loadBusy(..., { excludeAppointmentId })` so the old appointment/buffer does not block itself. `updateWithin(..., { patientTimezone, replaceSettledReminder: true })` moves in place, keeping price/status/`confirmedAt`; do not recheck the patient booking cap.
- Share `loadReschedulable` with session `GET /appointments/:id/slots` (strict `{ from, to }`); use `computeSlots` with `excludeAppointmentId`, removing the current start.

## Notifications and reminders

- Booking requests notify through their own queue `booking-request-notify` (`{ requestId, event }`, `enqueueBookingRequestNotifications` on `tx`; `deliverBookingRequestNotificationsNow` after commit without the scheduler): `received`/`nudge` to the provider on `reminderChannel` (no patient details, WhatsApp `TWILIO_WHATSAPP_USER_PORTAL_REQUEST_SID`, nudge `TWILIO_WHATSAPP_USER_PORTAL_REQUEST_NUDGE_SID` with the release time as `{{4}}`), `rejected`/`expired` to the patient, and `unconfirmed-expired` to the contact when the link was sent and never clicked (never to the provider). Workers reread and skip requests no longer in that state. `sweep-booking-requests` (15 min) expires stale holds per provider under `expireStaleWithin` and nudges once past half the hold (`nudgedAt` claimed with `updateMany`); `purge-booking-requests` deletes non-PENDING rows after 90 days and never-confirmed rows after 48h (`UNCONFIRMED_RETENTION_HOURS`). Stale UNCONFIRMED holds expire like the others but get no nudge.
- Every patient message follows one route: `resolvePatientRoute` (`src/portal/patient-route.ts`) gives `reminderChannel` when it has an address, else email, WhatsApp, SMS, never an unverified number; null means skip, and it is null once `messagesStoppedAt` is set. A request has no patient yet, so its notices (`confirm-link`, `unconfirmed-expired`, `request-rejected`, `request-expired`) go to the contact that sent it; `confirm-link` is the only message that carries the token (email body, or the bare `{{4}}` of the WhatsApp URL button) and nothing logs its variables. Render only through `renderPatientNotice` (`src/portal/patient-notices.ts`): patient WhatsApp templates are the `TWILIO_WHATSAPP_PATIENT_PORTAL_*_SID` (`CONFIRM_LINK` and `BOOKING_UNCONFIRMED` are the two Utility templates of the link flow, required with `requireEnv` like the others), and the meeting link reuses `{1: provider, 2: url}` of `TWILIO_WHATSAPP_PATIENT_APPOINTMENT_MEETING_LINK_SID`. Phone notices and portal SMS reminders carry the provider, the time and the place or link, never the appointment type, notes or the patient's name, and a template variable is never empty. WhatsApp reminders keep the approved template, which greets by name.
- Use `enqueuePortalNotifications(event, id, tx, previousStartAt?)`. `portal-booking-notify` payloads contain only ids/timestamps/kind; enqueue with `fromPrisma(tx)` so rollback removes jobs. Without the scheduler, send after commit, best effort.
- Workers reread appointments, skip deleted/wrong-state records (CANCELLED for cancellation, active otherwise), and throw on failed sends for retries. Reschedule notices skip superseded moves. Provider notices contain no patient details; WhatsApp templates use `TWILIO_WHATSAPP_USER_PORTAL_{BOOKING,CANCEL,RESCHEDULE}_SID`.
- A `PENDING` booking sends only the provider notice (`booked-link-pending`); the patient confirmation waits for `meeting-ready` (link set, or the "link will follow" fallback). A link set on a portal appointment fires `onMeetingLinkSet` in `updateWithin` (`meeting-ready` from `PENDING`, else `patient-meeting-link`); callers owning the transaction run `afterCommit` (scheduler off). Emails and reminders never print a placeholder for a missing link.
- Patient-facing notifications/reminders use `Appointment.patientTimezone ?? User.timezone`; provider text uses `User.timezone`. Do not add a full stop after formatted "a. m."/"p. m.".
- Enqueue `send-reminder` on `tx` when created or `sendAt`/`sendMode` changes (`startAfter: sendAt` for SCHEDULED). Never duplicate an unchanged job: simultaneous PENDING reads can send twice. Old jobs remain after moves; workers skip jobs more than a minute before the new `sendAt`.
- All cancellation paths call `cancelLinkedReminder(tx, ...)` for PENDING reminders; reactivation does not restore them. Workers cancel instead of sending reminders for deleted/inactive appointments.
- Portal appointments get their reminder from `portalReminder` (`src/portal/portal-booking.service.ts`) at the provider's `portalReminderTiming` booking setting, read on `tx` at booking, approval and reschedule. Its presets mirror the appointment modal's (`REMINDER_TYPE_CONFIG` in `Portal/src/types/Reminder.ts`); `portalReminderSendAt` (`src/portal/portal-reminder-timing.ts`) computes them, clock presets in the patient's zone. Keep both in step. None once the send time has passed or is not before the start.
- Rescheduling keeps PENDING reminder channel/address and moves `sendAt` (or cancels when the preset leaves no time, or is `NONE`). Settled SENT/FAILED/CANCELLED reminders are unlinked with audit and replaced by a new reminder on the patient's route, never rewritten.

## Time and frontend conventions

- Backend time math uses Luxon via `src/utils/time/time-utils.ts`. Spring gaps: `resolveLocalTime(...).exists === false`, `localToUtc` shifts forward; fall overlaps use the first occurrence. Resolve window edges per date, step in real minutes; never hand-roll offsets.
- Provider UI uses `user.timezone`. React components read `useDisplayTimezone()` and pass it explicitly to `src/utils/TimeUtils.ts`; implicit defaults are for non-React callers. `AuthContext` sets it; invalid zones fall back to browser time and report to Sentry. Do not use local `Date` getters/setters or bare `toLocale*String` on instants.
- Use `ZonedDatePicker` and `toPickerValue`/`fromPickerValue` (wall time held as UTC-mode dayjs). Calendar pages pass one timezone through hooks/views.
- Calendar days (birth/evolution-note dates) are UTC midnight, written with `calendarDayToIso`/`DateTimePicker mode="calendarDay"`, read with `calendarDayOf`/`fmtCalendarDay`/`getAge`, never through a timezone. Bare `YYYY-MM-DD` and `mode="localDate"` also represent calendar days.
- Public pages (`src/app/book/[slug]`) stay outside `(provider)`, with no `AuthProvider` or `/users/me` probe, and use `noindex`. Booking is anonymous end to end: need, time and details (`PatientDetailsStep`, "Último paso": name, Correo or WhatsApp, consent, CAPTCHA), then `BookingResult` ("Revisa tu correo"/"Revisa tu WhatsApp"), with no code step and no credentialed call. "¿Te equivocaste? Corregir" releases the hold with the `releaseToken` kept in state and returns to details with the form intact. The link opens `/book/confirmar/[token]` (`BookingConfirmationPage`, outside `[slug]`, `noindex`, `no-referrer`): it only reads until "Confirmar mi cita" is clicked, then shows confirmed, requested (approval or review), expired or unavailable. "Mis citas" and its link show only while `provider.selfServe`. `useBookingFlow` keeps the step in history (only its name) and `reachableStep` lands a stale entry on the furthest valid step; sheets use `useHistoryOverlay`, so back closes them. From 960px `BookingFlow` swaps `ProviderHeader` for the always-open `ProviderPanel` and passes Atrás to `StepScreen`; `test/setup.ts` matches no media query, so tests render phones unless they stub one. Keep `/book` outside `proxy.ts` matching (`test/proxy.test.ts`).
- Public pages are light only, even when a provider saved a dark theme in that browser: `<html>` stays dark and `data-theme="light"` on the `book` layout frame resets the tokens, so the frame also sets `color`, because `<body>` has already resolved its own. An undefined `--c-*` token falls back to the inherited color without any error. `test/utils/publicTheme.test.ts` guards the tokens and `e2e/tests/public/legibility.spec.ts` measures 4.5:1 on every screen, disabled controls included.
- Anonymous reads use `publicApi`/`usePublicQuery`, never provider `useApiQuery`/`fetchWithAuth`. Start, view, confirm and release use `publicApi` (anonymous, no credentials) through `src/api/portal/useBookingConfirmation.ts` with the token in the JSON body; view is a plain call, not a mutation, so StrictMode's doubled effect cannot trip the in-flight guard. Session calls (behind self-serve) use `portalApi`. Without a session, Mis citas shows the shared "no disponible" state: there is no login screen.
- Public UI uses the patient's device zone (`browserTimezone()`) explicitly: `src/utils/publicBooking.ts` supplies `slotQueryRange`, `slotWindow`, `lastBookableDateIn` and patient-date grouping. Reuse `useSlotChooser` + `SlotChooser` (`src/components/PublicBooking/`): slots load one `slotWindow` at a time (27 visible days, because the API allows 31 and `slotQueryRange` pads both ends) and accumulate, and empty windows stop at `MAX_EMPTY_WINDOWS`. Reschedule slots come from the session appointment endpoint, never public slots.
- `ContactChoiceField` offers Correo and WhatsApp on the details step. The public profile always reports `whatsappConfirmation: true` because both link SIDs are required; the Portal still hides WhatsApp when it is false. There is no code step, and patient copy never promises a channel beyond that choice (later messages follow `resolvePatientRoute`). A `409` about WhatsApp (caps) switches the form to Correo and shows the server message.
- Always show booking consent; never submit price/end/status. Map booking 409s to Spanish messages; a taken slot clears selection and reloads. Public 404s share the "no disponible" page. Cancel/reschedule 404 closes the action and refreshes; slot 404/409 returns to the list with the server message.
- Use in-app `ConfirmDialog` with its own `FocusTrapProvider` on public pages, never `window.confirm`. Keep the appointment being moved in component state, not the URL.
- E2E public projects seed `e2e-publica` via `db:seed-e2e`; the API needs `ENABLE_PORTAL=true` and runs with `ENABLE_SELF_SERVE=false`. Use `Portal/e2e/support/mock-brevo.mjs` (4010), `BREVO_API_BASE_URL=http://localhost:4010`, provider EMAIL reminders, and Cloudflare's test site key. Read `/__test/latest-link?to=` (the newest `/book/confirmar/<token>` URL; pass `not` to `latestLink` to wait for a newer one) and `/__test/messages`. Strip Vercel bypass headers from anonymous API calls.
- `db:seed-e2e` also seeds `e2e-aprobacion` (approval mode). Every seeded account gets the Server's `ADMIN_PASSWORD`, which the Portal e2e env supplies as `TEST_USER_PASSWORD` (they must match). Both portal providers log in through `openProviderPage` (`e2e/support/provider-context.ts`), never the shared SUPER_ADMIN. Shared steps live in `e2e/support/portal.ts`. Approval and review specs run only in the desktop `public` project; a run uses 8 starts (`portal-booking-ip`, 10/IP/15min) and 17 view/confirm/release calls (`booking-confirm-ip`, 20/IP/15min), so a spec adds no start or click it does not need. There is no Twilio mock in e2e: specs book by email and assert only that the WhatsApp choice is offered. Specs open the emailed link (`latestLink`) and assert nothing is booked before the click. Review data (a deleted patient) is created per run through the provider API, not seeded. The e2e job sets `PUBLIC_RATE_LIMIT_MAX` high because every request comes from one IP. It builds the Portal with `NODE_ENV=production` and `CSP_ENFORCE=true`, so specs run under the enforced CSP: `next build` keeps the job-level `NODE_ENV=test`, which would add `'unsafe-eval'` and hide what the policy blocks.

## Google connections

- Reuse `verifyConnection` for the daily check and `POST /google/connection/verify`; checks call Google and may write, so never use GET for verification.
- Expire only through `markConnectionExpired` (idempotent audit), classifying with `isAuthorizationFailure`. Encrypted refresh tokens cannot appear in `where`; `rotateRefreshToken` compares decrypted values and guards writes with `updatedAt`.
- Frontend branches on `status: connected | expired | not_connected`, not legacy `connected`; reconnect with `startOAuth(path, true)`. Google alerts are in-app only through `ProviderAlerts`/`PageLayout` for ADMIN/SUPER_ADMIN; never fetch the status endpoint for VIEWER (403).
